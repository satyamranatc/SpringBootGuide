Dependency Injection & IoC

Understand why constructor injection is preferred over field injection, how the IoC container manages objects, and what happens inside ApplicationContext.

  • Explicit dependencies: Prevents partially initialized objects and supports class immutability
  • Unit testing ergonomics: Easily instantiate services in tests without Spring test runners
  • Bean lifecycle: Instantiation → Populate properties → BeanNameAware → PostConstruct → Ready

@Service
public class UserService {
    private final UserRepository repository;

    // Constructor injection: explicit, immutable & easily mockable
    public UserService(UserRepository repository) {
        this.repository = repository;
    }
}

API Design Beyond CRUD

REST Semantics & RFC 7807

Move beyond generic GET/POST. Learn status code precision, HTTP idempotency, pagination strategies, and industry standard error formatting.

  • Status Codes: 200 (OK) vs 201 (Created) vs 204 (No Content)
  • Security Semantics: 401 (Unauthenticated) vs 403 (Forbidden / Insufficient Roles)
  • Idempotency: PUT replaces entire resource; PATCH updates partial fields
  • Pagination: Offset/Limit vs Keyset/Cursor for high volume datasets
Architecture Crucial

DTO Isolation & Java Records

Never expose JPA entities directly to API consumers. Avoid accidental data leaks, circular serialization loops, and tight DB coupling.

  • Entity vs DTO: Separation of database storage concerns from API contracts
  • Java Records: Immutable, boilerplate-free data transfer carriers
  • Mapping: Clean transformation via MapStruct without manual setter noise

Robustness Production

Validation & @RestControllerAdvice

Centralized error handling. Stop using scattered try-catch blocks in controllers. Handle Bean Validation failures cleanly.

  • Bean Validation: @Valid, @NotBlank, @Size, @Email
  • @RestControllerAdvice: Intercepts all controller exceptions in a single place
  • Unified JSON error payload with timestamp, HTTP status, and field errors
Java 
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException ex) {
        return ResponseEntity.status(404).body(new ErrorResponse(404, ex.getMessage()));
    }
}
JPA Internals Critical

Entity Lifecycle & Dirty Checking

Understand the 4 states of an entity: Transient, Persistent, Detached, and Removed. Learn how Hibernate detects mutations automatically.

  • Persistence Context: 1st-level cache scoped to the current EntityManager session
  • Dirty Checking: Hibernate compares snapshot copies at flush time and issues UPDATEs
  • save() vs saveAndFlush(): In-memory queuing vs immediate SQL push

    ↓ entityManager.remove()

Performance Killer Interview Must-Know

The Infamous N+1 Problem

Fetching 100 users generates 1 query for users and 100 queries for their orders (101 roundtrips). Learn the 4 concrete ways to eliminate it.

  • JOIN FETCH: Eagerly fetch associations in a single SQL inner/left join
  • @EntityGraph: Declaratively specify fetch plans per repository method
  • default_batch_fetch_size: Group lazy queries using SQL WHERE IN (...)
  • DTO Projections: Select only required fields directly from DB
Java Repository 
// Fixes N+1: Executes a single SQL query with JOIN
@Query("SELECT u FROM User u JOIN FETCH u.orders WHERE u.active = true")
List<User> findAllWithOrders();
Database Core Engineering

Transactions & ACID Boundaries

Deep dive into Spring's @Transactional, isolation levels, propagation semantics, and the dreaded self-invocation proxy bypass.

  • Rollback rules: By default, rolls back on unchecked (RuntimeException), NOT checked exceptions
  • Propagation: REQUIRED (join or start) vs REQUIRES_NEW (suspend & spawn)
  • Self-invocation trap: Calling a transactional method from within the same class bypasses the proxy!
  • readOnly = true: Optimization hint that disables Hibernate dirty checking snapshots
SQL Tuning Mastery

SQL Optimization & EXPLAIN Plans

Stop guessing why a query is slow. Inspect database query execution plans, design composite indexes, and detect deadlocks.

  • EXPLAIN: Inspect type (ALL vs ref vs const) and rows scanned
  • Composite Indexes: Order matters! Leading columns must match WHERE clauses
  • Covering Index: All required columns reside in the B-Tree index, avoiding table lookups
Security Architecture

Spring Security Beyond JWT

Deconstruct the SecurityFilterChain, authentication vs authorization, SecurityContextHolder, password hashing, and token rotation.

  • SecurityFilterChain: Ordered chain of servlet filters intercepting every HTTP request
  • BCrypt: Adaptive slow hashing with salt to prevent rainbow table attacks
  • Token Rotation: Short-lived Access Token (15m) + secure Refresh Token in HTTP-only cookie
  • Method security with @PreAuthorize("hasRole('ADMIN')")
Testing Essential

Testing Pyramid & Slices

Stop manually testing endpoints with Postman. Build automated test suites with Mockito, MockMvc, and Testcontainers.

  • Unit Tests: Fast JUnit 5 + Mockito (@Mock, @InjectMocks)
  • Web Slice: @WebMvcTest tests controllers without loading full context
  • Integration: Testcontainers spins real MySQL & Redis in Docker for real test fidelity
Observability Production

Logging, MDC & Actuator

Replace System.out.println() with structured logging, MDC request tracing across microservices, and Prometheus metrics.

  • MDC Correlation IDs: Inject unique request ID to trace a call from Controller → Service → DB
  • /actuator/health & /actuator/metrics for Kubernetes readiness/liveness
  • Micrometer integration pushing latency histograms directly to Prometheus & Grafana
Distributed Senior Tier

Caching, Async & Architecture

Master Redis Cache-Aside, @Async worker thread pools, direct S3 pre-signed uploads, and Hexagonal / Clean architecture.

  • @Cacheable & Redis: Cache-aside pattern with TTL to prevent cache stampedes
  • @Async: Decouple heavy operations using custom ThreadPoolTaskExecutor
  • Direct S3 Uploads: Generate pre-signed PUT URLs so clients upload directly to S3

Challenge 1: Fetching 100,000 Records

Calling GET /jobs loads 100k database entities directly into JVM heap, triggering high GC pauses, massive memory consumption, and API timeouts.

3,850ms → 14ms
p99 Latency (99.6% faster)
✕ Bad: Full Heap Load Memory: 480MB • Latency: 3.8s 
// Catastrophic at scale: Pulls all 100k rows into RAM
@GetMapping("/jobs")
public List<Job> getAllJobs() {
    return jobRepository.findAll();
}
✓ Optimized: Keyset / Pageable + DTO Memory: 4MB • Latency: 14ms 
// Production ready: Keyset pagination with DTO projection
@GetMapping("/jobs")
public Page<JobSummaryDTO> getJobs(
    @RequestParam(defaultValue = "0") int page,
    @RequestParam(defaultValue = "20") int size
) {
    return jobService.getJobsPaged(PageRequest.of(page, size, Sort.by("createdAt").descending()));
}
Engineering Takeaway: Never expose unbounded collection endpoints. Always enforce pagination limits, apply covering indexes on sorting columns (created_at), and use light DTO projections instead of heavy entities.

Challenge 2: The N+1 Query Multiplier

Iterating through 100 applications to get the applicant's profile triggers 1 query for applications, plus 100 individual queries for users, destroying database throughput.

101 Queries → 1 Query
DB Roundtrips (99% saved)
✕ Bad: Lazy Loading Loop 101 DB Queries • 2,400ms 
// Fires 1 query for applications, then 100 queries for users!
List<Application> apps = appRepository.findAll();
for (Application app : apps) {
    System.out.println(app.getUser().getEmail());
}
✓ Optimized: JOIN FETCH / EntityGraph 1 Single Query • 18ms 
// Executes 1 single SQL INNER JOIN in the database
@Query("SELECT a FROM Application a JOIN FETCH a.user WHERE a.job.id = :jobId")
List<Application> findAllWithUserByJobId(@Param("jobId") Long jobId);
Engineering Takeaway: Log SQL statements in dev (spring.jpa.show-sql=true). Count the generated queries. Solve child entity loading with JOIN FETCH or configure default_batch_fetch_size: 50.

Challenge 3: Slow SQL Query & EXPLAIN Plans

Filtering 500k candidate applications by email and status does a full table scan without composite indexes, locking table rows and spiking CPU.

1,200ms → 2ms
Execution Time (600x faster)
✕ Bad: Full Table Scan type: ALL • rows: 500,000 
-- No composite index: Database reads 500,000 disk pages
EXPLAIN SELECT * FROM applications 
WHERE email = 'dev@spring.io' AND status = 'ACCEPTED';
✓ Optimized: Composite B-Tree Index type: ref • rows: 1 
-- Create covering composite index on search predicate
CREATE INDEX idx_app_email_status ON applications(email, status);

-- Now uses index range scan: Zero table scan
EXPLAIN SELECT * FROM applications 
WHERE email = 'dev@spring.io' AND status = 'ACCEPTED';
Engineering Takeaway: Run EXPLAIN before committing any new query. If type is ALL on a high-cardinality table, an index is missing. Put the most selective column first in composite indexes.

Challenge 4: High-Traffic Endpoint & Redis Cache

A trending company's public job listing is hit 1,000 times per second. Hitting MySQL for every request exhausts Hikari connection pools.

85ms → 1.2ms
Response Latency (70x faster)
✕ Bad: Repeated DB Hits 1,000 req/s • DB CPU 98% 
// Slams database with identical queries every millisecond
public CompanyProfileDTO getCompany(Long id) {
    return companyRepository.findById(id)
        .map(mapper::toDto)
        .orElseThrow();
}
✓ Optimized: Redis Cache-Aside + TTL Redis Memory • DB CPU 3% 
// Cache-aside: hits Redis in RAM; falls back to DB only on miss
@Cacheable(value = "companies", key = "#id", unless = "#result == null")
public CompanyProfileDTO getCompany(Long id) {
    return companyRepository.findById(id)
        .map(mapper::toDto)
        .orElseThrow();
}
Engineering Takeaway: Always define an explicit TTL (Time-To-Live) on cache keys to prevent memory leaks and stale data. Pair with @CacheEvict when entities are updated.

Challenge 5: Large File Upload (Direct S3 Pre-Signed)

Streaming a 5GB video/resume file through Spring Boot exhausts worker threads, buffers files to app disk, and creates a severe denial-of-service vector.

Zero App IO & Memory
Serverless Direct Upload
✕ Bad: Proxy Through App Server Server RAM Spikes • Thread Blocked 
// Holds Tomcat thread open for 4 minutes during upload
@PostMapping("/upload")
public String upload(@RequestParam MultipartFile file) {
    s3Client.putObject(bucket, file.getOriginalFilename(), file.getInputStream());
    return "Uploaded";
}
✓ Optimized: Pre-Signed S3 URL Latency: 2ms • Zero Server IO 
// App returns temporary signed URL; Client uploads directly to S3!
@GetMapping("/resumes/upload-url")
public UploadUrlResponse getPresignedUrl(@RequestParam String filename) {
    String presignedUrl = s3Presigner.generateUrl(filename, Duration.ofMinutes(15));
    return new UploadUrlResponse(presignedUrl);
}
Engineering Takeaway: Never route multi-gigabyte payloads through application servers. The application should only authorize and generate pre-signed URLs, letting Amazon S3 or Cloud Storage handle the raw IO directly.

Challenge 6: 10-Second Blocking Request (Async Worker)

Triggering AI resume parsing and email notifications synchronously within the HTTP request blocks the servlet thread for 10 seconds, quickly causing thread starvation.

10,000ms → 12ms
HTTP API Response Time
✕ Bad: Synchronous Heavy Loop Tomcat Threads Starved • 10s wait 
// HTTP Client hangs for 10 seconds waiting for AI parse
@PostMapping("/apply")
public Response apply(@RequestBody ApplicationRequest req) {
    aiResumeService.parseAndScore(req.getResumeId()); // Takes 10s!
    emailService.sendConfirmation(req.getEmail());     // Takes 1.5s!
    return Response.ok();
}
✓ Optimized: Event Queue + @Async 202 Accepted • 12ms 
// Returns HTTP 202 immediately; worker processes in background
@PostMapping("/apply")
public ResponseEntity<Void> apply(@RequestBody ApplicationRequest req) {
    applicationService.savePending(req);
    eventPublisher.publishEvent(new ApplicationSubmittedEvent(req));
    return ResponseEntity.accepted().build(); // 12ms response
}
Engineering Takeaway: Separate fast write operations from slow downstream processing. Publish an asynchronous event or push to Kafka/RabbitMQ so worker threads process the heavy lifting in the background.

● SECTION 23: INTERVIEW QUESTION VAULT

Senior Interview Question Bank

Can you explain and defend these concepts without Googling? Filter by category or search in real-time to test your technical depth.

🔍
Q01 Why is constructor injection preferred over field injection? Spring
▼

Constructor injection makes all dependencies explicit at creation time, enforces class immutability (allowing final fields), prevents partially initialized objects, and makes unit testing effortless without needing reflection or Spring's test context runner.

Interview Tip: Field injection (@Autowired private UserService s;) hides dependencies from unit tests and makes it easy to violate the Single Responsibility Principle without noticing.
Q02 What does @SpringBootApplication actually do? Spring
▼

It is a meta-annotation bundling three core annotations: @Configuration (identifies the class as a source of bean definitions), @EnableAutoConfiguration (guesses and configures beans based on jar dependencies on the classpath), and @ComponentScan (scans the current package and sub-packages for @Component, @Service, etc.).

Q03 How does Spring Boot's auto-configuration evaluate which beans to load? Spring
▼

Auto-configuration uses conditional annotations such as @ConditionalOnClass, @ConditionalOnMissingBean, and @ConditionalOnProperty. For instance, if DataSource.class is on the classpath and you haven't declared your own DataSource bean, Spring Boot automatically creates a HikariDataSource bean.

Q04 What is the Spring Bean Lifecycle? Spring
▼

1. Instantiation (calling constructor) → 2. Populating properties/dependencies → 3. Aware interfaces (BeanNameAware, ApplicationContextAware) → 4. BeanPostProcessor pre-initialization → 5. @PostConstruct / InitializingBean → 6. BeanPostProcessor post-initialization (AOP proxies created here!) → 7. Bean ready for use → 8. @PreDestroy on shutdown.

Q05 PUT vs PATCH: What is the exact semantic difference? REST
▼

PUT is idempotent and replaces the target resource entirely with the request representation (any omitted fields are reset or overwritten). PATCH applies a partial modification to the resource, modifying only the fields provided in the payload.

Q06 HTTP 401 Unauthorized vs 403 Forbidden: When do you return which? REST
▼

401 Unauthorized means the request lacks valid authentication credentials (user identity is unknown or token expired). 403 Forbidden means the user is authenticated, but lacks the required roles/permissions to access the specific resource.

Q07 When should an API return HTTP 204 No Content? REST
▼

When the server has successfully fulfilled the request and there is no additional content to send in the response payload. Commonly used for successful DELETE operations or update actions where returning the modified object is unnecessary.

Q08 Explain the N+1 problem and how to solve it in production. JPA
▼

The N+1 problem occurs when fetching N parent records results in 1 initial query for the parents, followed by N separate queries to fetch the lazy-loaded child associations (1 + N = 101 queries for 100 rows). It is resolved by: 1. Using JOIN FETCH in JPQL to eagerly load children in a single SQL query. 2. Using @EntityGraph. 3. Configuring hibernate.default_batch_fetch_size to batch load IDs via SQL IN (...). 4. Projecting directly to a flat DTO.

Q09 What is Hibernate Dirty Checking and how does it work? JPA
▼

When an entity is loaded into the Persistence Context, Hibernate creates an internal snapshot of its state. During transaction commit or flush, Hibernate compares the entity's current property values with the snapshot. If changes are detected ("dirty"), it automatically generates and executes an SQL UPDATE statement without requiring an explicit repository.save().

Q10 save() vs saveAndFlush(): What is the difference? JPA
▼

save() attaches the entity to the Persistence Context and queues the SQL insert/update until flush time (typically at the end of the transaction). saveAndFlush() immediately synchronizes in-memory state with the database, issuing SQL statements right away within the active transaction.

Q11 What is EXPLAIN in SQL and how do you read it? Database
▼

EXPLAIN reveals the execution plan chosen by the database optimizer. Key columns to inspect: 1. type: ALL (Full table scan — danger!), index (Full index scan), range, ref, or const (Fastest). 2. key: The actual index used. 3. rows: Number of rows estimated to be examined.

Q12 When can an index actually hurt database performance? Database
▼

Every index consumes disk space and must be updated synchronously on every INSERT, UPDATE, and DELETE. On write-heavy tables with multiple redundant indexes, write throughput drops significantly and index fragmentation increases.

Q13 Why BCrypt instead of SHA-256 or MD5 for passwords? Security
▼

SHA-256 and MD5 are designed to be fast, making them vulnerable to GPU-accelerated brute-force attacks (billions of hashes/sec). BCrypt is an intentionally slow, adaptive key-derivation function with an adjustable cost factor and automatic cryptographic salting to defeat rainbow table attacks.

Q14 Where should JWT validation happen in Spring Security? Security
▼

Inside a custom OncePerRequestFilter positioned before UsernamePasswordAuthenticationFilter in the SecurityFilterChain. The filter extracts the Bearer token from the Authorization header, verifies the signature, and populates SecurityContextHolder.getContext().setAuthentication(auth).

Q15 How would you handle 10,000 requests per second in Spring Boot? Production
▼

1. Horizontal scaling: Deploy multiple stateless instances behind an Nginx/ALB load balancer. 2. Caching: Offload read traffic with Redis Cache-Aside. 3. Database: Read replicas with read-write splitting and properly tuned HikariCP connection pool. 4. Asynchronous processing: Push heavy work to Kafka/RabbitMQ message queues. 5. Rate limiting: Bucket4j / Redis token buckets to protect against DDoS. 6. Java 21 Virtual Threads (spring.threads.virtual.enabled=true) for high I/O throughput.

Q16 What causes a Spring Boot database connection pool timeout? Production
▼

HikariCP throws ConnectionTimeoutException when all available connections in the pool are held by active requests and none are returned within the timeout window (default 30s). Common causes: 1. Slow unindexed database queries holding connections open. 2. Running external HTTP/REST calls inside @Transactional methods. 3. Connection leaks where resources aren't properly closed.

Senior Pro Tip: Never execute third-party HTTP API calls or slow file I/O inside a @Transactional boundary. It monopolizes a database connection from Hikari for the entire network roundtrip!
